# Sanitize Skill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a `/sanitize` superpowers skill that analyzes Swift files in a directory for syntax and structure issues, presents a report for approval, then applies fixes.

**Architecture:** A single SKILL.md file installed in `~/.claude/skills/sanitize/`. The skill instructs a two-phase pipeline: Phase 1 dispatches an analysis agent that uses git to find changed Swift files and builds a report; Phase 2 applies approved fixes file by file after user confirmation.

**Tech Stack:** Superpowers skill system (Claude Code), Bash (git diff), Swift file analysis via agent reasoning

## Global Constraints

- No auto-commit — all git actions are the user's responsibility
- Report must be shown before any file is modified
- Only `.swift` files are touched
- Scope is directory-level only (not single file, not full project)
- No dashes in any user-facing copy or string literals in the skill output

````markdown
# Sanitize

## Overview

Cleans Swift code (including SpriteKit) in a directory. Two phases: analyze first, fix only after approval. Uses git to skip unchanged files, saving tokens.

## Invocation

```
/sanitize <directory>
```

If no directory argument is provided, use the folder containing the currently open file in the IDE.

---

## Phase 1: Analysis

### Step 1: Find changed Swift files

Run the following to find which Swift files to analyze. Replace `<directory>` with the argument the user provided.

```bash
LAST_SANITIZED=$(git log --oneline --grep="#sanitized" -1 --format="%H" 2>/dev/null)
if [ -z "$LAST_SANITIZED" ]; then
  git diff --name-only HEAD -- "<directory>/**/*.swift" 2>/dev/null | grep "\.swift$"
else
  git diff --name-only "$LAST_SANITIZED" HEAD -- "<directory>/**/*.swift" 2>/dev/null | grep "\.swift$"
fi
```

If the output is empty, respond with:
```
Nothing to sanitize. No Swift files changed since the last #sanitized commit.
```
Then stop. Do not proceed to analysis.

### Step 2: Analyze each file

For each file in the list, read its full contents. Check for every issue in the tables below. Record each match with its line number, category, short title, what is wrong, the exact fix to make, and one sentence explaining the consequence if left unfixed.

**SYNTAX issues:**

| Issue | How to detect | Fix |
|---|---|---|
| Force unwrap | `!` directly after a variable name — e.g. `foo!` or `foo!.bar`. Exclude `!=` comparisons. | Replace with `guard let` or `if let` |
| Unused import | An `import X` statement at the top of the file where no symbol from module X appears anywhere in the file body | Remove the import line |
| Redundant type annotation | `let x: SomeType = literal` or `var x: SomeType = literal` where Swift can infer the type from the right-hand side | Remove `: SomeType` from the declaration |
| Commented-out code | 3 or more consecutive lines beginning with `//` that contain Swift syntax (not documentation comments or `// MARK:`) | Remove the entire block |
| Dead variable | A `let x = ...` or `var x = ...` where `x` is never referenced after its declaration within the same scope | Remove the declaration |
| Unnecessary self | `self.propertyName` or `self.methodName()` in a non-escaping closure or regular method body where Swift does not require `self.` | Remove `self.` |

**STRUCTURE issues:**

| Issue | How to detect | Fix |
|---|---|---|
| Function too long | Any `func` body spanning more than 50 lines | Extract logic into smaller named methods |
| File too large | Total line count exceeds 300 | Suggest splitting into focused files by responsibility |
| Vague naming | Variables or parameters named: `data`, `temp`, `info`, `stuff`, `manager2`, `helper`, `obj`, `val`, `res`, `result2`, `item2` | Rename to an intent-revealing name |
| View doing business logic | A SwiftUI `var body: some View` block containing `URLSession` calls, Firestore reads/writes, `@AppStorage` mutation, or direct model state changes | Move the logic into a ViewModel |
| SpriteKit all inline | An `SKNode` or `SKScene` subclass where a single method exceeds 80 lines and handles setup, physics, and game logic together | Extract into named methods — one per responsibility |

### Step 3: Build and display the report

Format the report exactly as shown below. Omit files that have no issues.

```
SANITIZATION REPORT  <directory> (<N> files analyzed)
═══════════════════════════════════════════════════════════

<Filename.swift>
  Line <N>  <SYNTAX|STRUCTURE>   <Short title>
            Issue:   <What is wrong>
            Fix:     <Exact change to make>
            Why:     <One sentence consequence if left unfixed>

<NextFilename.swift>
  [issues listed the same way]

───────────────────────────────────────────────────────────
SUMMARY: <N> files  |  <N> issues  (<N> syntax, <N> structure)
Proceed with fixes? (yes / skip <filename> / cancel)
```

If no files have issues, respond:
```
All changed Swift files look clean. Nothing to fix.
```
Then stop.

Wait for the user's response before making any changes.

**User responses:**
- `yes` — apply fixes to all listed files
- `skip <filename>` — exclude that file, apply fixes to the rest (can be chained: `skip Foo.swift skip Bar.swift`)
- `cancel` — abort immediately, make no changes

---

## Phase 2: Fix

Apply fixes only to files the user approved. Work one file at a time in this order:

1. Read the file
2. Apply every approved fix for that file
3. Write the updated file
4. Print: `<filename>  <N> fixes applied`
5. Move to the next file

Do not touch any skipped files. Do not commit any changes.

When all files are done, print:

```
SANITIZATION COMPLETE
Files fixed: <N>
Total issues resolved: <N> (<N> syntax, <N> structure)

Review your changes: git diff
When satisfied, commit with a message containing #sanitized to set the baseline for next run.
```
````
